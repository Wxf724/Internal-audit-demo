# 内审平台标准重构方案 V2

日期：2026年10月23日  
项目：D:\飞书\内控检查系统\内控系统\InternalControl  
交付：结构与交互方案；本轮不修改业务代码。

## 1. 已确认范围与设计结论

用户已确认：
- 服务单一企业的内部审计部门。
- 首版同时覆盖财务审计、工程审计、经济责任审计。
- 目标为面向客户演示的完整前端原型。

因此，本方案采用“一个企业、统一项目主线、三类专业业务、完整演示闭环”。不建设集团层级、多租户和事务所客户管理；真实生产后端不作为本轮交付前提。

上一版文档可作为背景分析；页面结构与实施范围以本V2为准。

建议重建信息架构，形成六个业务工作区：工作台、审计计划、审计项目、审计整改、审计资源、统计分析。系统管理放在独立管理入口。原16个菜单不能简单全部换名保留，页面中的有效能力按业务对象重新归位。

“标准”指以内部审计业务要求为基础的产品设计建议。准则不会统一规定六个菜单、八个页签或固定复核层数，审批及适用依据可配置。

## 2. 当前结构为什么不适合直接改名

静态核查涉及 AppShell.tsx、routeMeta.tsx、router/config.tsx、业务页面、workflowStore.ts 和 taskDispatchStore.ts。

| 当前问题 | 具体表现 | 重构决策 |
| --- | --- | --- |
| 年度安排和项目方案混杂 | 工作计划表单已有组长、成员、抽样方法、重点领域；还承担审批、拆解和派发 | 年度计划只负责年度项目安排；审计组和程序归项目准备 |
| 项目主对象缺位 | 以计划关联检查任务，缺少统一项目详情 | 新建审计项目，所有执行记录归项目 |
| 操作入口分散 | 任务中心和派发中心各自承担执行前准备 | 取消两者独立菜单，合并进项目准备和项目内分工 |
| 同一层混放不同概念 | 智能审查是工具，穿行是方法，底稿是成果，却并列成菜单 | 按项目工作组织；工具与方法嵌入审计程序 |
| 资料与档案混杂 | 数据采集同时维护资料需求、数据包、归档材料清单和字段映射 | 资料收集归资料管理，档案检查归项目档案，字段映射收进数据分析的高级设置 |
| 证据与资料概念混杂 | 上传资料、取证单和证据台账缺少明确层次 | 文件先是资料，经选择、核验并关联程序或底稿后作为证据使用 |
| 审批脱离业务材料 | 审核中心另占全局入口，与首页待办和页面审批重复 | 工作台统一汇总待办；点击进入对应业务对象的复核视图 |
| 报告时序错误 | 报告中心仅将已整改事项作为可编制来源 | 审计报告基于项目结论；整改情况报告分开 |
| 模板与规则维护重叠 | 检查标准库和知识库均含方法、模板、法规引用 | 合并到审计资源，明确程序、模型、文书、法规、案例的分工 |
| 首页信息不聚焦 | 新闻轮播、集团新闻、通知、指标和业务待办同时铺陈 | 删除新闻宣传区，保留个人办理和必要提醒 |
| 看板口径不一致 | 部分看板使用旧模拟数据与固定日期，首页又使用另一套状态 | 指标由同一业务数据派生，支持下钻 |
| 演示操作未真正闭环 | 部分暂存、生成、复核、报送主要提示或本地计步 | 每个动作更新同一业务对象并可跨页面追踪 |

年度计划与项目审计方案本身是不同层次的安排，应在产品中拆开。[R1] 报告应在执行必要程序后形成，并经过意见征求及复核，而不是等全部整改完成才编制。[R3]

首版同时开放财务、工程、经济责任三类项目。类型通过项目筛选和专业字段体现，不再为每类审计复制整套一级菜单。内控专项等可后续按同一机制扩展。

## 4. 页面布局标准

### 4.1 全局框架

~~~text
┌──────────────────────────────────────────────────────────┐
│ 企业名称 / 内部审计管理平台            通知  当前用户       │
├──────────┬───────────────────────────────────────────────┤
│ 工作台   │ 面包屑 / 页面标题 / 主要操作                    │
│ 审计计划 │                                               │
│ 审计项目 │ 页面主体                                       │
│ 审计整改 │                                               │
│ 审计资源 │                                               │
│ 统计分析 │                                               │
│          │                                               │
│ 管理入口 │                                               │
└──────────┴───────────────────────────────────────────────┘
~~~

决策：
- 使用固定左侧主导航，取消当前顶部分类切换、侧栏随分类出现或消失的结构。
- 顶部只承担品牌、通知和用户身份；不再重复一套业务菜单。
- 全局导航保持稳定，进入项目后在内容区显示项目页签。
- 列表、编辑、复核、报告采用不同布局，不把每页都做成卡片拼盘。
- 页面仅有一个主要滚动区；底稿和报告编辑器在确有需要时拥有独立编辑滚动。
- 延续现有蓝白灰与组件体系；不用新闻宣传轮播、装饰大屏或多层卡片填满空间。
- 基准适配1366×768，1920×1080扩展显示；窄屏允许表格合理横向滚动、侧栏折叠，重要操作不被遮挡。
- 状态用文字与颜色共同表达；复核意见、阻塞原因、关联对象应可直接查看。

### 4.2 五种页面模板

| 页面类型 | 标准布局 | 适用页面 |
| --- | --- | --- |
| 台账 | 标题及操作 → 筛选 → 表格 → 分页 | 年度计划、项目、整改、资源 |
| 项目概览 | 项目抬头 → 阶段 → 当前待办 → 重点情况及近期记录 | 项目概览 |
| 执行工作区 | 左侧程序或对象树 → 主编辑区；证据按需抽屉打开 | 程序执行、测试、底稿 |
| 复核 | 业务材料主区域 → 复核意见及操作区 | 方案、底稿、报告及整改核验 |
| 报告 | 左侧目录 → 正文编辑或预览；意见和引用按需打开 | 报告编制及反馈处理 |

重要性提醒保留在对象上下文内，不把每条记录都包成独立卡片。台账点击行进入有独立URL的详情；抽屉适合快速查看和关联选择，长报告、底稿及复杂方案使用完整页面。

## 5. 各工作区的职责与布局

### 5.1 工作台

目的：当前用户今天需要办理什么。

布局：
- 顶部最多四项个人摘要：待处理、退回修改、临近期限、进行中项目。
- 主体为待办表格，按全部、待我处理、我发起的、已处理切换。
- 下方展示我的项目，支持按审计类型和项目阶段筛选。
- 侧部或下方显示资料催办、复核退回、整改超期等重要提醒，不常驻大面积图表。

待办列：事项类型、标题、所属项目、当前节点、发起人、提交时间、办理期限、操作。
动作：办理、查看来源、查看处理历史。
办理跳转到真实对象的复核视图；同一待办在工作台、项目概览只出现同一条任务。

删除当前新闻图片轮播、集团新闻、机构宣传和与当前用户无关的排行榜。业务通知可保留在通知入口。

### 5.2 审计计划

目的：安排本企业年度审计工作。

年度计划列表：年度、计划版本、计划状态、计划项目数、已启动数、负责人。
年度计划详情：计划说明、计划项目表、资源汇总和批准记录。
计划项目列：拟开展项目、审计类型、对象、选项依据、预计季度、预计人日、项目负责人、启动情况。

创建年度计划不要求填写样本、底稿、具体程序或完整审计组。这些属于项目准备。
项目储备只保存候选与选项理由，可纳入年度计划。
审计对象按部门、业务、工程项目和被审计人员分类管理，使用单企业部门结构，不展示集团—子公司层级。

动作：新建年度计划、增加计划项目、提交批准、申请调整、启动项目。
一个计划项可按范围拆为多个项目，但创建时明确关联；普通演示场景默认一项对应一个项目。经授权的临时项目可直接立项并补充来源，不强制伪造年度计划项。

### 5.3 审计项目台账与新建项目

项目台账是审计人员的主入口。
筛选：年度、审计类型、阶段、负责人、对象、关键字。
列：编号、项目名称、审计类型、主要对象、审计期间、负责人、当前阶段、下一待办、计划完成日期。
默认表格；卡片或甘特不列为首版必需视图。

新建项目使用三步：
1. 基本信息：类型、名称、来源、关联计划、对象、审计期间和实施时间。
2. 专业信息：按财务、工程或经济责任动态展示。
3. 审计组：负责人、主审、成员与分工，确认后进入项目准备。

“审计期间”是被检查业务所属期间，“实施时间”是审计人员实际工作时间；经济责任审计另有任职期间，三者不能混为一个日期字段。

### 5.4 项目工作台八个页签

| 页签 | 主要内容 | 核心操作 | 不应承担的职责 |
| --- | --- | --- | --- |
| 概览 | 项目范围、阶段、成员、当前待办、里程碑、重点风险和近期记录 | 继续办理、查看阻塞 | 不再次编辑全部底稿或堆放所有台账 |
| 审计准备 | 审前调查、风险重点、方案、程序清单、组内分工、回避声明、通知及送达 | 编制方案、导入程序模板、提交复核、生成通知 | 不再次创建年度计划 |
| 资料管理 | 需求清单、责任人、截止日、文件提交、接收与补件、可用数据集 | 发需求、催办、上传、接收或退回 | 不管理报告归档清单 |
| 审计实施 | 审计程序、执行记录、样本测试、分析任务、疑点核验、底稿 | 执行、选择证据、编制底稿、提交复核 | 不把模型命中直接认定为正式问题 |
| 审计发现 | 草稿、核实、复核、分类、金额、意见反馈、报告纳入情况 | 登记发现、补证、沟通、提交复核 | 不用整改状态覆盖审计认定结论 |
| 审计报告 | 类型化正文、发现引用、征求意见、反馈处理、复核、签发与送达 | 编制、征求意见、处理反馈、送审、签发、下载 | 不要求全部整改完成才能编制 |
| 整改跟踪 | 本项目对应任务、方案、进度、佐证、核验、延期和重开 | 下达、反馈、催办、核验、销号 | 不复制全局整改台账 |
| 项目档案 | 通知、方案、程序、底稿、证据、发现、报告、审批及送达记录的索引 | 完整性检查、组卷、归档、调阅 | 不重新收集同一份材料 |

八个页签是工作空间，不是每页必须按顺序锁死的向导。资料和证据可持续补充，重大事项可提前沟通，整改可以边审边改。锁定只针对需受控的正式版本和业务动作。

### 5.5 审计实施工作区详设

~~~text
项目抬头与阶段
项目页签：概览 准备 资料 [实施] 发现 报告 整改 档案
┌────────────────┬───────────────────────────────────────┐
│ 程序目录        │ 程序标题、负责人、状态、目标及依据      │
│ 资金收支        │                                       │
│  ├ 付款真实性   │ 执行记录 / 样本测试 / 分析任务 / 底稿   │
│  └ 重复付款     │                                       │
│ 资产管理        │ 当前执行与判断                         │
│ ...             │ 关联证据、异常及结论                    │
│                 │ 保存 / 登记发现 / 提交底稿复核          │
└────────────────┴───────────────────────────────────────┘
证据选择、模型选择和关联材料通过按需抽屉打开。
~~~

每个程序定义审计目标、关注风险、方法、负责人、计划时间、执行结果与结论。
人工检查、穿行、抽样和数据分析都是执行方法，不要求每个程序都运行AI。
疑点可以认定为无异常、待补证、转底稿或关联既有底稿。
底稿允许正常结论；不因未发现问题就阻塞程序完成。
正常程序的记录、结论和复核同样保留。底稿是支撑结论与报告的工作记录，需保存必要索引和复核意见。[R2]

分析模型只需让审计人员选择模型、数据及参数，并查看结果。字段映射、模型运行配置、输出映射等技术项收进授权高级配置，不作为客户默认办理流程。

### 5.6 发现与报告

发现详情主区域：事实、依据、原因、影响、建议；补充分类、严重程度、相关金额、责任部门和所需期限。
侧部按需显示关联程序、底稿、证据及沟通记录。
金额区分涉及金额、确认损失、追回或节约金额，避免自动等同。
“责任认定”仅在需要的项目类型中出现，与问题严重程度分开。
经核实的发现可纳入报告；未查清疑点保留为线索，不写成确定事实。

报告页面由目录和正文为主，结构按项目类型加载。正文引用已复核发现，保留引用时版本。
意见采用“意见项—涉及章节或发现—补证—采纳结论—处理说明”结构，支持采纳、部分采纳、不采纳。
报告和发现意见关联，但不相互替代。
报告必要程序为编制、征求意见、反馈核实、复核、签发送达。[R3]

审计报告与整改情况报告分别管理；后者在整改工作区汇总，不增加独立报告中心菜单。审计结束、报告已送达、成果已归档、整改完成分别记录。

### 5.7 审计整改

保留全局整改入口，因为整改周期可能超过项目实施期，需要跨项目跟踪。
布局：筛选栏、到期与超期摘要、任务表格；详情使用全页。
列：任务编号、发现、来源项目、类型、责任部门、责任人、期限、自报状态、核验状态、下一动作。

责任人提交措施、阶段进展和佐证；审计方核验后销号。
支持退回、延期申请与审批、长期整改阶段目标、已销号事项重开。
不得把“上传佐证”直接等同于“核验通过”。纠正问题由管理层负责，审计方评价措施及效果。[R4]

一般在报告正式送达后批量下达整改，批准的边审边改事项允许提前下达并记录依据。每次下达有事件记录，重复操作不重复创建任务。

### 5.8 审计资源与统计分析

资源分工：
- 法规依据：来源、条款、适用范围、生效与失效时间。
- 程序模板：目标、风险、方法、执行步骤、所需资料和底稿结构。
- 文书模板：通知、方案、底稿、报告、整改表、档案目录。
- 分析模型：输入数据、参数、疑点输出及版本。
- 审计案例：脱敏背景、发现、证据逻辑、处理与整改结果。

程序模板复制到项目时形成项目版本；资源后续更新不能悄悄改变已经批准的项目程序或已签发报告。

统计分析使用普通业务页面：
- 计划与项目：批准计划、启动、实施、报告送达情况，按三类型比较。
- 发现与成果：分类、部门、金额口径、重要发现和相关证据索引。
- 整改：到期任务、按期核验销号、超期、延期、复发。
所有图表可点击进入相应筛选台账。首版不保留装饰性大屏、无依据风险总分和无法解释的“全覆盖”宣传指标。

## 6. 三类审计的专业差异

共用项目、资料、程序、证据、底稿、发现、复核、报告和整改；差异通过对象、专业字段、程序模板、执行界面和报告章节体现。

| 维度 | 财务审计 | 工程审计 | 经济责任审计 |
| --- | --- | --- | --- |
| 主要对象 | 部门或业务范围、账套及财务期间 | 建设工程项目及其阶段、合同和结算 | 被审计人员、岗位、任期及履职范围 |
| 专业字段 | 账套、会计期间、科目、凭证、收支与资金、往来、资产 | 概算或预算、合同、变更签证、进度款、结算送审及审定情况 | 姓名、岗位、任职期间、职责分工、重大决策与管理事项 |
| 典型程序 | 收支真实性、支付授权、往来核验、资产和费用 | 招采、合同、变更、工程计量、付款及结算 | 职责履行、重大决策、经营目标、资产资金管理、风险管理 |
| 执行界面 | 凭证及明细账、业务关联、异常核验 | 工程—合同—变更—付款—结算关系与对比明细 | 职责—事项—决策参与—证据—评价与责任分析 |
| 发现补充 | 科目、凭证、交易及期间 | 合同、变更或结算项、计量或金额差异 | 涉及人员、职责、任期、决策过程、行为与后果证据 |
| 报告特点 | 财务情况、审计结果、结论与建议 | 工程基本情况、阶段、合同及造价相关结果、管理问题 | 基本及履职情况、评价、主要问题、责任分析、意见建议 |

这些是首版产品模板建议，不是所有类型的完整审计程序清单。
经济责任审计不能做成“财务审计加一个姓名”；其核心是任职期间的经济责任履行及相关事实评价。[R5] 对国有企业等适用对象，应结合相应准则和干部管理权限；真实客户为其他所有制企业时，应核对授权和适用制度。

演示数据按单一企业设计：财务部、采购部、工程管理部、运营部门及内部管理人员，不出现集团子公司树。

首版三套演示主场景：
1. 财务：付款分析发现重复支付疑点，关联凭证与审批记录，编制底稿、核实发现、出具报告并跟踪整改。
2. 工程：核查变更签证与合同付款，发现资料或计量依据不足，补证、复核、形成工程审计发现及报告。
3. 经济责任：围绕任期内重大采购或投资决策，关联职责、会议、审批和执行结果，完成沟通反馈、责任分析及报告。

工程示例是情景数据，不以任意比例自动认定核减；经济责任示例不通过金额或职位自动判定责任。

## 8. 状态与交互闭环

项目阶段：待启动 → 准备中 → 实施中 → 报告中 → 审计实施完成。
报告、整改与档案各自独立状态，避免一个“完成”覆盖全部含义。

| 对象 | 主要状态 |
| --- | --- |
| 年度计划 | 草稿、待批准、已批准；调整生成新版本 |
| 方案 | 草稿、待复核、退回、已批准 |
| 程序 | 未开始、执行中、待补证、待复核、已完成 |
| 底稿 | 草稿、待复核、退回、复核通过、归档锁定 |
| 发现 | 草稿、核实中、待复核、已认定、不予认定 |
| 报告 | 草稿、征求意见、反馈处理中、待复核、待签发、已签发、已送达 |
| 整改 | 待方案、方案确认中、整改中、待核验、退回、已销号 |
| 档案 | 待整理、待检查、已归档；追加材料保留记录 |

关键规则：
- 提交复核产生真实待办，办理或退回同步改变原对象和所有列表。
- 对象不存在时显示无法找到与返回入口，不回落到第一条模拟记录。
- 生成底稿创建底稿ID；不以跳转或弹窗代替生成。
- 数据分析结果、审计发现和整改任务是不同对象，不一键跳过认定。
- 发现撤回或不予认定需处理报告引用和预建整改；已签发事项走受控更正。
- 正常结论可以完成程序并支撑报告，不强制生成问题。
- 未完成整改不阻止报告签发与已形成成果归档。
- 所有对象ID、当前项目、筛选和返回位置在导航中保持一致。

## 9. 前端原型交付范围

本轮采用统一演示数据源和角色视图，支持刷新后的演示进度恢复；不用每页单独写一份同名模拟数据。
上传、下载、编辑、提交、复核、退回、签发、下达及销号应有真实的前端行为与关联变化。

角色视角：
- 审计负责人：计划、重要复核、报告和统计。
- 项目负责人或主审：项目准备、程序分工、实施和报告组织。
- 审计人员：分配程序、资料、证据底稿和发现。
- 被审计部门联络人或整改责任人：资料、意见及整改反馈。
- 管理员：资源及配置。

角色切换为演示辅助能力，与业务导航分开；前端权限用于展示职责差异，不宣称代替真实服务端鉴权。

建议准备一个年度计划、六个不同阶段的项目，三类各两个，覆盖准备、实施、报告和整改；每类至少有一条可连续操作的演示路径，另含无问题、退回、异议、延期及重开场景。
使用一个虚构企业及合理关联的示例附件，金额、日期、项目编号和报告内容一致。
演示控制中的重置与场景预置放在独立辅助入口，不混入客户日常业务按钮。

文件：
- 上传后可在本对象及关联页面看到并预览或下载。
- 浏览器所选文件若需刷新保留，采用适当的本地文件存储，不只保存虚假的成功状态。
- 通知书、报告与档案目录提供可用的下载或打印输出，不以提示“导出成功”结束。
- 不在用户可见正文放接口说明、mock状态、开发阶段或未实现提示。

## 10. 实施顺序与验收

### A. 框架和对象先行
重建左导航、项目工作台路由、年度计划与项目、三类型专业字段和统一数据。
验收：在三个类型间切换，字段、对象和程序模板有实质区别，项目上下文不丢失。

### B. 项目办理闭环
迁移准备、资料、程序、测试、分析、底稿和发现，补齐复核。
验收：从资料和程序产生真实底稿、关联发现；退回、补证、正常结论可操作。

### C. 报告与整改闭环
补齐三类报告、征求意见、反馈、复核、签发、送达、整改、档案及统计。
验收：报告尚有未完成整改时也可正常送达；整改核验后统计和来源项目同步更新。

### D. 清理与客户演示验收
移除旧入口、确认未使用代码，统一样式、数据和操作反馈，按角色演示三个场景。
验收清单：
1. 新建年度计划与立项分开，临时项目有合理入口。
2. 财务、工程、经济责任都有专属字段、程序与报告。
3. 同一发现的底稿、证据、报告和整改双向可追溯。
4. 复核从待办进入原对象，意见及退回原因可查。
5. 无问题项目可完成；不同样本结果不串改。
6. 征求意见支持采纳、部分采纳及不采纳说明。
7. 签发、送达、成果归档和整改完结不混为一个状态。
8. 项目页与全局整改页操作同一数据。
9. 所有按钮均有实际行为、校验和状态反馈；无效按钮删除。
10. 页面刷新、直接打开详情及返回列表都保持合理状态。
11. 1366×768可完成办理，不出现被遮挡操作或多层滚动困局。
12. 清理后完成类型检查、lint、构建和三场景演示回归。
