# 内控检查系统改造为内审平台方案

编制日期：2026年10月23日  
分析对象：D:\飞书\内控检查系统\内控系统\InternalControl  
范围：现有前端静态核查、业务定位、功能、流程和实施顺序。本次仅新增方案文档，未修改业务代码，未验证外部后端和线上系统。

## 1. 改造结论

建议定位为“内部审计管理平台”，以审计项目为主线，贯通年度计划、项目准备、审计实施、审计报告、整改跟踪和成果运用。现有采集、分析、取证、底稿、问题和整改页面可作为基础。

核心变化：

1. 从“检查计划—检查任务”扩展为“审计对象—年度计划—审计项目—实施方案—审计程序”，过程材料统一归属项目。
2. 从控制点核验扩展为多种审计方法，保留内部控制审计，并逐步支持采购、财务收支、投资工程和经济责任等业务。
3. 将当前围绕已整改事项生成的报告，拆分为审计报告、整改情况报告和后续审计报告。
4. 补齐风险选项、实施方案、报告征求意见、异议核实、质量复核、独立性与回避、档案调阅。
5. 将模拟数据和页面状态迁移到统一业务数据与服务端状态控制，落实权限、版本及操作留痕。

本方案默认面向国内央国企，与现有工程定位一致。菜单、字段、状态和开发优先级属于产品设计建议；审批主体、签发权限、办理时限与档案要求需按目标单位制度配置，不是所有企业通用的法定程序。

## 2. 内控与内审的区别

内部控制是组织为实现目标而建立并执行的管理过程；内部审计对经济活动、内部控制和风险管理等开展独立、客观的监督、评价和建议。[S1][S2]

| 比较项 | 内部控制 | 内部审计 | 产品改造影响 |
| --- | --- | --- | --- |
| 核心问题 | 业务如何规范运行、如何控制风险 | 经营管理是否合规有效、风险是否得到控制 | 从控制点检查扩展到目标、程序和审计结论 |
| 责任主体 | 治理层、经理层及员工共同实施，业务部门落实控制 | 内部审计机构及人员独立开展，向适当治理和领导主体报告 | 分开审计方、被审计方、复核和签发角色 |
| 工作载体 | 制度、流程、授权、控制矩阵、日常监督及自评 | 年度计划、项目、程序、证据、底稿、报告 | 增加独立审计项目主对象 |
| 主要范围 | 控制措施的设计与运行 | 财务收支、经营管理、绩效、投资、内控和风险管理等 | 审计类型与程序模板可配置 |
| 工作方式 | 持续嵌入业务，也开展定期评价和专项检查 | 项目审计、专项审计、跟踪审计，也可持续分析 | 不能只按事后检查设计 |
| 常见产出 | 控制矩阵、缺陷台账、内控评价报告 | 审计底稿、发现、报告、建议及后续评价 | 审计问题不全部等于控制缺陷 |
| 整改责任 | 业务及管理部门实施改进 | 被审计单位整改，审计机构跟踪评价效果 | 审计人员不代替业务部门执行整改 |

内控并非只管事前，内审也并非只管事后。内部控制审计可以成为内审平台的一类业务；内控自我评价与内部审计应保留各自的目的、责任主体和结论口径。[S1][S2]

采购示例：内控侧设置供应商准入、采购授权、合同审批、验收付款控制；内审侧核验实际执行，进一步检查交易真实性、采购价格合理性和异常供应商关系，以证据支撑审计结论。发现疑点不等于已认定舞弊。

## 6. 内审全流程

以下是便于建设平台的通用分解。不同单位可合并阶段、调整名称；沟通、重大风险报告、质量复核和档案收集贯穿全过程。

~~~mermaid
flowchart TD
    A[审计对象与风险评估] --> B[年度计划与项目储备]
    B --> C[项目立项与审计组]
    C --> D[审前调查与项目审计方案]
    D --> E[审计通知与资料准备]
    E --> F[程序执行与数据分析]
    F --> G[取证和工作底稿]
    G --> H[发现核实与底稿复核]
    H --> I[报告草拟与征求意见]
    I --> J[反馈核实与报告复核]
    J --> K[签发和送达]
    K --> L[整改落实与督办]
    L --> M[效果核验与后续审计]
    K --> N[审计成果归档]
    M --> O[整改与后续材料补充归档]
    M --> A
    O --> A
    F -.边审边改和重大事项报告.-> L
~~~

年度计划与项目审计方案需区分；风险评估为选项和资源安排提供依据。[S3] 下表的字段与完成条件是本方案的落地建议。

| 阶段 | 主要工作 | 主责 | 产物及完成条件 |
| --- | --- | --- | --- |
| 1 对象与风险评估 | 汇总单位、业务、项目，结合金额、历史问题、变化和管理关注识别风险 | 审计管理 | 对象库、风险评估、选项依据，保留人工判断 |
| 2 年度计划 | 排项目、时间、预算及人力，履行批准程序，管理临时项目及调整 | 审计负责人 | 批准计划、项目储备、调整记录 |
| 3 项目立项与组建 | 明确类型、对象、审计期间、目标、组长与成员，检查回避 | 项目负责人 | 主档、分工、独立性或回避声明 |
| 4 审前调查与方案 | 了解业务、制度、数据及历史问题，确定范围、重点、程序、方法及排程 | 审计组 | 批准的项目审计方案、程序清单和变更版本 |
| 5 通知与准备 | 通知送达、进场沟通、资料需求与接收 | 审计组、被审计单位 | 通知、回执、资料清单、数据接收记录；具体顺序按制度安排 |
| 6 审计实施 | 访谈、检查、观察、盘点、函证、穿行、控制测试、实质性测试及分析 | 审计人员 | 程序记录、样本、异常线索，方法按目标选择 |
| 7 证据与底稿 | 保存证据，记录过程、判断、结果和限制，开展复核 | 编制及复核人员 | 可追溯底稿和证据，正常结论也记录 |
| 8 发现核实 | 整理事实、依据、原因、影响及建议，核实金额与管理责任 | 审计组 | 经核实发现、沟通及补证；疑点不能直接定论 |
| 9 报告征求意见 | 汇总项目结论，形成征求意见稿，记录反馈与争议 | 审计组、被审计单位 | 征求意见稿、反馈、采纳或不采纳处理记录 |
| 10 复核签发与送达 | 处理异议，完成所需复核、签发，控制接收范围并记录送达 | 复核及授权签发人员 | 正式报告、问题清单、建议、送达及版本 |
| 11 整改与督办 | 明确责任、措施、时限和阶段目标，提交说明及佐证，管理延期 | 被审计单位整改，审计机构跟踪 | 整改台账、整改情况报告、督办记录 |
| 12 效果评价 | 核验落实及有效性，按风险安排后续审计，销号或重开 | 审计机构 | 核验结论、必要的后续报告、重开及复发记录 |
| 13 归档与成果运用 | 成果及时归档，整改和后续材料补入；总结共性问题，反馈制度与计划 | 项目组、档案人员 | 档案、调阅、成果台账与知识反馈 |

通知、证据、底稿、沟通、报告、后续审计分别有对应具体准则支撑。[S4]—[S9] 穿行用于了解流程和控制，不能仅凭一次穿行认定整段期间控制均有效；抽样应记录总体、方法、选择理由及结论范围。[S10]

### 6.1 报告与整改的时序

审计报告以实施必要程序后形成的证据与结论为基础，正式报告需履行征求意见、必要修改及复核等程序；可以披露审计期间整改情况，但全部整改完成不应成为一般审计报告编制的统一前置条件。[S8]

建议分开：

- 审计报告：审计方编制，关联项目及发现，说明审计结果和建议。
- 整改情况报告：责任单位提交，关联一个或多个整改任务，审计方核验。
- 后续审计报告：审计方根据后续审计实施结果形成，评价纠正措施与改进效果。[S9]

允许边审边改，仍保留发现时事实、沟通及整改前后证据。报告签发、成果归档和整改完成分别管理，不因长期整改而一直不归档已形成成果。

## 7. 数据对象与状态

建议对象关系：

~~~text
审计对象与风险评估
 └─ 年度计划 / 储备项目
     └─ 审计项目 projectId
         ├─ 成员、独立性声明、通知及送达
         ├─ 方案版本 → 程序 → 执行任务 / 测试 / 样本
         ├─ 资料需求 → 接收数据包版本
         ├─ 分析运行 → 疑点 → 人工核验
         ├─ 底稿 ↔ 证据（多对多）
         ├─ 审计发现 ↔ 底稿 / 证据（多对多）
         ├─ 报告版本 ↔ 发现快照 / 征求意见 / 反馈
         ├─ 整改任务 → 措施 / 佐证 / 核验 / 后续审计
         └─ 档案卷、审批和操作事件
~~~

跨项目分析可查看多个项目；底稿和正式发现应有明确主项目归属。引用其他项目材料需核查权限并保存版本。

| AuditProgramVersion | projectId、版本、风险、重点、方法、批准记录、生效时间 |
| AuditProcedure | 方案版本、目标、风险、方法、负责人、状态、结论、关联底稿 |

| AuditWorkpaper | projectId、程序、样本、编制人、执行记录、结果、结论、证据、复核记录 |
| AuditFinding | projectId、事实、依据版本、原因、影响、分类、严重程度、建议、底稿及反馈 |
| AuditReport | projectId、reportType、版本、发现快照、征求意见、复核、签发、送达 |
| RectificationTask | projectId、findingId、责任单位与人员、措施、期限、阶段目标、自报及核验状态 |
| ApprovalTask | businessType、businessId、业务版本、节点、处理人、结果、意见、时间 |

一项发现可由多份底稿支撑，一份底稿可支持多个发现；整改可含多项措施。不要将现有单一 workpaperId、rectificationId 固定为所有场景的一对一关系。

状态建议：

- 项目阶段：待立项 → 准备中 → 实施中 → 报告中 → 审计实施完成；暂停、延期、终止另设受控操作。
- 报告：草稿 → 征求意见 → 反馈处理中 → 待复核 → 待签发 → 已签发 → 已送达；退回相应编辑阶段并留版本。
- 底稿：草稿 → 待复核 → 退回补充 / 复核通过 → 归档锁定。
- 发现：草稿 → 核实中 → 待复核 → 已认定 / 不予认定。整改进度另存。
- 整改：待反馈方案 → 方案确认中 → 整改中 → 待核验 → 退回继续整改 / 已销号；长期、阶段完成及延期单独标识。
- 归档：未归档 → 待检查 → 已归档；补充材料按追加或新版本留痕。

页面可显示“报告已发、整改跟踪中”，已签发报告及其历史结论保持原版本。

## 8. 角色与质量控制

| 角色 | 主要职责 | 建议限制 |
| --- | --- | --- |
| 审计负责人及授权治理主体 | 计划、重大事项与报告审批签发 | 按组织制度配置路线 |
| 项目负责人、主审 | 方案、分工、进度、复核和报告组织 | 不用个人按钮代替所有层级复核 |
| 审计人员 | 执行、取证、底稿、发现草稿 | 不自行完成对自编事项的独立复核 |
| 质量复核人员 | 规定范围内的方案、底稿、发现或报告复核 | 访问限授权项目，保留退回意见 |
| 被审计单位联络人 | 提供资料、确认相关事实、反馈意见 | 不能修改审计底稿、结论及已签发报告 |
| 整改责任人 | 提报方案、进度及佐证 | 不能自行核验销号 |
| 档案人员 | 组卷、保管、授权调阅 | 不能直接改写锁定结论 |
| 系统管理员 | 账号、组织、配置和运维 | 管理权限与材料查看权限分开 |

独立性与报告关系应落到授权和规则中。[S2] 复核层级按单位制度、项目与风险配置；现有一级、二级、交叉复核可复用，不应写成全部项目固定的法定层级。[S6][S8]

## 9. 智能能力

| 环节 | 可辅助 | 人工确认点 |
| --- | --- | --- |
| 准备 | 历史问题、资料清单、法规检索、程序草拟 | 目标、范围、程序 |
| 分析 | 勾稽、重复付款、异常价格、供应商关系线索 | 数据完整性、异常解释及证据 |
| 底稿 | 整理附件、引用位置、起草过程及事实 | 编制核对与独立复核 |
| 报告 | 汇总通过复核的发现，校验金额和引用 | 征求意见、判断及签发 |
| 整改 | 清单检查、逾期提醒、可能复发识别 | 实际改进效果及核验 |

AI与规则仅形成疑点或草稿。保存来源、数据版本、规则或模型版本、引用、人工修改与处置。置信度不能代替审计结论。现有 sourceFindingIds 可作追溯起点，需要真实运行和引用记录支撑。

## 10. 实施顺序

### 第一阶段：重建审计业务主链

交付项目主档、计划与项目关系、方案和程序、真实证据底稿关系、报告与整改分离、征求意见及复核。

沿用现有结构，逐步新增项目与程序模块，保持必要路由兼容；WorkflowStages.tsx 按计划、项目准备和实施职责拆分。

代码落点：

- src/pages/icm/AppShell.tsx：定位、菜单、项目上下文。
- src/pages/icm/routeMeta.tsx、src/router/config.tsx：导航及项目详情。
- src/pages/icm/data/types.ts、src/pages/icm/store/workflowStore.ts：对象、关系及状态。
- src/pages/icm/pages/ReportCenter.tsx：项目报告、征求意见、反馈和签发。
- src/pages/icm/pages/Workpaper.tsx、WalkthroughWorkbench.tsx、ReviewWorkbench.tsx：实际创建关联对象，替换页面局部模拟闭环。
- src/api/：基于现有封装增加项目、底稿、报告及整改接口。

验收：一个采购专项审计从计划或授权临时立项开始，执行程序、形成底稿、认定发现、处理反馈、签发报告并形成待整改事项；报告签发时允许整改未完成。

### 第二阶段：正式业务能力

联通或建设后端、数据库、文件存储、统一身份与数据权限；服务端校验状态迁移、复核权限、重复提交、并发版本和日志。

补齐文书导出、送达、档案、调阅、整改核验、延期及重开。浏览器存储可改善演示，但不能替代服务端授权和正式档案。

验收：刷新及重登数据一致；权限有效；报告能追溯当时底稿及证据版本；重复提交不重复生成任务；关键动作留痕。第一、二阶段可以并行，正式上线需具备相应基础能力。

### 第三阶段：专业及智能扩展

扩展财务、投资工程、经济责任、信息系统、绩效等模板，增加跨系统分析、模型、覆盖评估、共性问题与成果运用。

验收：按类型加载相应对象、方案、程序、评价依据、字段和报告结构，共用证据、底稿、复核及整改基础能力。经济责任等专业类型不能只增加一个名称选项。

## 11. 关键验收场景

1. 有问题项目：线索、核验、证据、底稿、复核、发现、报告与整改可双向追溯。
2. 无问题项目：正常结论可留底稿、出具适当项目报告并归档，不强行生成问题。
3. 有异议：保留意见、补证、核实与采纳理由，依制度推进，不要求被审计单位必须同意全部结论。
4. 报告已发但整改未完：成果可归档，整改持续跟踪，报告保留原版本。
5. 退回及复发：补证、再次核验、重开或关联新发现，历史记录可查。
6. 多项目多样本：切换不串改结果，不回落默认底稿。
7. 权限分离：编制不能越权复核，被审计方不能改结论，整改责任人不能自核销号。
8. 版本和异常：补证、方案变更、报告更正、重复提交及并发编辑可追溯。

指标口径建议：计划完成率明确已批准项目分母；按期整改率以统计期应到期事项为分母；风险覆盖率先定义对象和风险范围；整改成果金额应有审核依据，不把发现涉及金额直接累计为“挽回损失”。
