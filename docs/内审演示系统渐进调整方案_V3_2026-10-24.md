## 一、已确认约束与最终判断

已确认：
1. 服务单一企业内部审计部门，覆盖财务、工程、经济责任三类审计。
2. 交付客户演示前端原型，重视展示质量、操作顺序和数据闭环。
3. 保留首页新闻轮播、集团新闻、宣传区。
4. 保留顶栏菜单；点击后展示相应左侧菜单。首页及看板可沿用当前无侧栏布局。
5. 顶栏切换演示角色，仅三个角色：审计负责人、项目负责人（主审）、审计人员。
6. 菜单可以合理拆分和调整归属，不能为减少菜单而硬合并不同职责。
7. 无动画展示。保留新闻轮播容器，图片直接切换，不滑动或淡入。
8. 尽量复用组件和页面骨架，不实施V2的大规模界面重构。

判断：不需要重建全局框架，不需要把所有页面搬进八页签项目工作台。保留现有分页面办理方式，通过共同项目上下文、统一数据和角色权限串联。必要的业务调整集中在计划/项目分层、项目准备、底稿复核、报告时序、外部反馈登记和归档。

“标准”是有清晰业务边界和可追溯流程的产品方案，不表示准则统一规定这些菜单和审批层级。页面布局是设计目标，实际美观与适配仍需实施后浏览器验证。

## 二、改造规模和复用边界

### 2.1 可以直接复用

- AppShell 顶部、侧栏、折叠方式、页面容器及既有主题。
- IcmPageKit 的 PageFrame、Card、Kpi、Tag、Toolbar、Segmented、DataTable、DetailLine、StepList。
- 公共 Button、Input、Textarea、Tabs、Modal、Pagination、SearchableSelect、DatePicker、DateRangePicker、TreeSelect、Tree。
- IcmChart 的 EChart 容器及 ResizeObserver 自适应逻辑。
- 页面已有列表、搜索、详情、来源追溯、证据预览、审批记录和报告正文等展示片段。
- 当前 React、TypeScript、Vite、React Router、Zustand 技术体系和请求封装。不为演示另装一套UI库。

复用展示组件不代表复用原有模拟操作。底稿本地计步、跳转代替生成、提示代替保存、报告从整改生成等逻辑必须调整。

### 2.2 必须做的业务修改

| 调整 | 必要性 | 最小做法 |
| --- | --- | --- |
| 计划与项目分层 | 年度安排与单项目执行混在同一表单 | 年度计划保留在原页，任务中心变项目中心；组队、程序移到准备页 |
| 项目统一关联 | 当前部分页使用各自数据、默认第一条对象 | 增加 projectId 和共享上下文；各页面读取同一项目数据 |
| 程序与任务归项目 | 只有计划—任务不足以组织不同审计类型 | 项目准备维护程序及分工，不新建独立任务平台 |
| 角色和复核 | 同一用户点击多次便完成复核不适合角色演示 | 产生真实审批任务，切换对应角色后办理 |
| 报告与整改分开 | 当前报告只能来自已整改事项 | 报告关联项目及发现，整改报告单独类型 |
| 外部材料登记 | 无被审计方角色，不能模拟其登录提交 | 审计侧登记收到的资料、反馈及整改材料 |
| 项目档案 | 全项目归档不能等同单份报告归档 | 增加一个轻量档案页面，复用表格、标签和完整性检查 |
| mock集中 | 当前数据分散且有固定业务日期 | 一套业务数据、状态操作、版本及时间来源，各页派生展示 |

### 2.3 本轮不扩大的范围

不新增多租户、集团组织管控、复杂资源调度、流程设计器、独立智能体平台或生产后端。已有集团新闻作为信息栏目保留，不据此增加集团组织权限体系。
不强制改名所有 icm 文件夹或重写全部CSS。先将可用页面接入正确数据，再逐步拆分过大的 WorkflowStages.tsx。

年度计划、全局知识库和首页不强制显示当前项目条。

从全局列表进入详情必须带真实对象ID；切换项目先检查未保存编辑，再清理不属于新项目的对象选择。对象不存在时显示找不到和返回入口，不显示第一条记录。

### 4.2 三角色原则

| 角色 | 默认数据范围 | 主要工作 |
| --- | --- | --- |
| 审计负责人 | 本企业授权审计项目及总体情况 | 年度计划审核、方案批准、重要发现与报告审核签发、重大整改及归档审核 |
| 项目负责人（主审） | 自己负责或被授权参与的项目 | 项目准备、程序分工、底稿/发现复核、报告编制、反馈处理、整改核验组织 |
| 审计人员 | 自己参与的项目及分配事项 | 资料登记、程序执行、取证、底稿与发现草拟、整改核查记录 |

三个演示角色分别映射到独立示例人员。角色切换改变当前身份、数据范围、待办与操作权限，不替换整套数据、不自动推进状态。
是否能办理同时判断角色、项目成员关系、任务受理人、当前状态和编制人；不能只看一个role字符串。
主审自己编制的底稿提交给其他合格复核人员，不能切换到同一人的另一个角色实现自审。负责人审核的同一业务也应遵守配置的职责分离规则。
方案/报告示例采用主审编制、负责人审核签发，仅为演示配置，不声称所有单位的真实批准权都属于该角色。

### 4.3 “同一页面分角色看”的具体规则

- 表头显示当前身份与项目，不另建三套页面文件。
- 有查看权限但无办理权限时，正文只读，显示处理节点及原因；不堆放可点击的无效按钮。
- 无项目访问权限时显示权限说明和返回入口；不改成另一个项目欺骗用户。
- 页面内“提交复核”和审核中心“通过/退回”调用同一状态操作。
- 切换角色时保留当前项目和详情；仍有访问权限就留在原位置，否则显示权限说明。
- 角色切换是原型演示能力，不改动现有登录token和共享 localStorage.user。

## 七、三类审计的最小专业差异

保留同一套组件，通过类型配置选择字段、表格列、程序模板和报告章节，避免三套复制页面。

| 差异 | 财务审计 | 工程审计 | 经济责任审计 |
| --- | --- | --- | --- |
| 项目专业信息 | 账套、财务期间、业务范围 | 工程名称、建设阶段、预算/概算、合同范围 | 被审计人员、岗位、任期、职责 |
| 程序示例 | 付款真实性、重复支付疑点、往来与资产 | 招采、合同、变更、计量、付款与结算 | 履职、重大决策、资金资产管理、风险管理 |
| 测试明细 | 凭证、账目、交易和附件 | 合同、变更签证、计量、付款、结算项 | 职责、决策事项、会议参与、审批和执行结果 |
| 发现专业字段 | 凭证、科目、期间及交易编号 | 工程/合同/变更/结算项、差异及依据 | 关联人员、任期、职责及责任分析证据 |
| 报告内容 | 财务情况、结果、评价与建议 | 工程情况、范围阶段、管理和造价相关结果 | 履职情况、评价、问题、责任分析和建议 |

不同类型不只有名称差异；经济责任不由职位与金额直接推断责任，工程不按固定比例自动核减。
审计期间、实际实施日期、任职期间分别保存。
这些是演示业务模板，不是全部专业审计程序或统一适用的法律责任认定规则。

## 八、mock数据设计：同一数据、真实动作、可恢复

### 8.1 一套业务对象

~~~text
年度计划 → 计划项 → 审计项目
                       ├─ 成员、方案版本、程序、执行任务
                       ├─ 资料需求 → 收到文件 → 可用数据集
                       ├─ 分析运行 → 疑点
                       ├─ 测试样本与结果
                       ├─ 取证记录及证据 ↔ 底稿
                       ├─ 审计发现 ↔ 底稿及证据
                       ├─ 报告版本 → 意见反馈 → 审核 → 签发/送达
                       ├─ 整改任务 → 收到方案/进展/佐证 → 核验
                       └─ 档案索引及补充卷
各提交对象 → 审核任务 → 处理意见 → 操作事件
~~~

文件、底稿和发现支持多对多关联，不把所有关系锁成单个workpaperId。
项目中心展示项目，程序任务才属于tasks；不把原任务数组直接换个变量名当全部项目。
维护一个权威业务数据来源。可以按职责拆文件或store，但不能分别维护同名计划、底稿或发现的平行数组。

### 8.2 最小实施方式

保留Zustand；将业务store组织成项目、执行、成果等切片或模块，共用业务对象及ID。
UI本地状态仅用于选中行、筛选、打开弹窗、尚未提交的表单草稿；正式mock记录进入共享store。
角色上下文另存，不能让角色切换重置业务数据。
持久化使用独立命名空间，如internal-audit-demo:v3:business、internal-audit-demo:v3:view；不覆盖共享登录user键。
附件二进制用浏览器IndexedDB或明确的静态示例文件，不能只持久化失效的blob URL。
增加schemaVersion和种子版本；格式不兼容时提供明确迁移/重置入口，不悄悄丢弃用户操作。
编号用稳定唯一ID，展示编号可读；不用数组长度计算ID。动作记录当前操作者、操作时间、对象版本和原因。
业务日期使用统一演示基准日或真实当前日期，页面明确统计截止日期；不继续散布固定2026年7月23日。

### 8.3 状态操作

示例动作：
- submitPlan / approvePlan / startProject
- saveProgram / submitProgram / approveProgram / assignProcedure
- createDemand / registerReceivedFile / acceptFile / requestSupplement
- runAnalysis / dispositionClue / saveTestResult / createWorkpaper
- submitWorkpaper / reviewWorkpaper / createFindingDraft / confirmFinding
- createProjectReport / issueConsultation / registerExternalOpinion / resolveOpinion / submitReport / signReport / registerDelivery
- issueRectification / registerExternalProgress / recordVerification / requestCloseOut / approveCloseOut / reopenRectification
- checkArchive / submitArchive / approveArchive

每个提交操作执行：权限与范围检查→校验状态及版本→校验必填→更新业务对象→创建或关闭待办→写事件→返回ID或明确错误。
只显示成功提示而不更新对象不算完成。审批待办已经处理、来源版本已变或当前角色不符时应阻止重复写入。
跨页数量由selectors派生，不每页手工加一减一。

### 8.4 外部反馈如何演示

被审计部门不是第四个角色。预置部分已收到的外部资料/意见/整改反馈，并保存提供部门、提供人和附件。
需要演示新增时，主审或人员点击“登记收到反馈”，选择样例反馈或上传文件并填写收到日期。
事件记录“李娜登记收到工程管理部提交的反馈”，不写成“李娜代表工程管理部提交”。
尚未收到的事项保持待反馈。不能切换角色或点击下一步自动伪造对方意见。
责任部门名称、外部责任人和期限仍在台账正常展示。

### 8.5 三套主场景与样例规模

建议六个项目，财务、工程、经济责任各两个；阶段覆盖准备、实施、报告、整改和已归档。
每类至少有一条可连续办理的主线；为主审和人员配置不同参与范围，角色切换能看出真实差异。

| 场景 | 可执行路径 | 核查重点 |
| --- | --- | --- |
| 财务 | 明细账/付款资料→重复支付疑点→核验底稿→发现→报告→整改核验 | 数据运行与疑点追溯，不把重复标记直接当损失 |
| 工程 | 合同与变更资料→测试与补证→底稿退回重提→发现→工程报告 | 补证、版本、工程专业明细 |
| 经济责任 | 任期职责与决策材料→履职程序→沟通与反馈→责任分析→报告 | 任期、职责、参与过程和事实证据 |

另外预置：无问题底稿、无问题项目、未收到意见、已收到异议、整改逾期、延期待审、整改核验退回、已销号重开。
样例附件与正文、编号、日期、金额相互一致。演示重置仅清理本原型命名空间，保留登录信息与其他应用数据。

## 九、操作顺序与闭环验收

### 9.1 正常主线

1. 主审：从计划创建或直接建立项目，维护成员、方案和程序。
2. 负责人：审核方案；批准后产生人员分工待办。
3. 人员：登记收到资料，执行程序/分析/测试，编制底稿。
4. 主审：通过或退回底稿；核实人员草拟发现。
5. 主审：汇总项目报告，发出征求意见并登记收到的反馈，说明处理。
6. 负责人：审核签发报告；主审登记送达。
7. 主审：按正式发现下达整改跟踪任务；人员登记收到的材料及核查结果。
8. 主审/负责人：按分工核验销号；项目成果归档、整改材料补充归档。

每一步均在现有页面完成，通过关联入口跳转，不为演示强制把一个流程塞到一个页面。

### 9.2 必须验证的异常和边界

- 无问题：底稿和程序可以完成，报告能形成，不强制生成发现或整改。
- 无AI：人工程序可直接执行和取证，不被“运行分析”按钮卡住。
- 退回：意见可查、版本递增、原待办关闭、重提交生成正确待办。
- 多样本：修改样本A不影响样本B；切换项目不带出别项目材料。
- 三角色：身份切换不改变数据和审核节点；编制人不能审核自己的同一份底稿。
- 外部反馈：未收到时不凭空通过；登记人和提供人明确区分。
- 报告整改：报告可在整改未完成时签发送达；整改变化不改写原报告正文。
- 全局一致：首页、审核中心、报告、整改与看板同一状态。
- 刷新与深链：刷新、直接打开详情、浏览器返回、切换顶栏都能找到真实对象。
- 重复提交：不重复生成项目、底稿或整改任务；并发旧版本编辑能识别。
- 归档：项目材料自动索引，引用固定版本，持续整改进入补充卷。
- 文件：能打开、预览、下载，不能只有文件名或“导出成功”。

## 十、组件渲染与无动画规范

### 10.1 组件复用的最小增补

建议只补三项跨页能力：
1. DemoRoleSwitch：顶栏三角色选择和当前示例身份。
2. ProjectContextBar：项目名称、类型、阶段、切换及关联导航。
3. ReviewPanel：统一处理意见、历史、通过/退回；业务详情和审核中心共用。

三者是已有控件的组合，不引入新UI库。表格如需补充rowKey、空状态、分页和键盘入口，扩展现有DataTable，不另造表格体系。
图表沿用EChart，默认关闭animation并保证明确容器高度；新闻图片比例固定，避免切图时跳动。

### 10.2 布局目标

- 保留现有专业蓝白灰和页面密度；统一页标题、筛选栏、表格行高、标签及按钮。
- 主内容容器min-width:0；侧栏一般约200—240px，辅助区约260—300px，屏宽不足收进抽屉或纵向，不把正文挤成窄列。
- 正文约14px、表格13—14px、辅助信息12px以上；长标题换行或带完整查看，不遮挡操作。
- 首要动作每个业务状态一般突出一个；其他动作用次级按钮或更多菜单。
- 1366×768、1440×900、1920×1080检查顶栏、侧栏、正文、页脚和弹窗；小屏允许合理表格横向滚动。
- 列表页避免页面和多张卡片层层滚动。报告/底稿确需分区滚动时，保持标题和操作可见。
- 首页宣传区保留，待办与资讯分区清楚；角色摘要和待办优先级可以变化，新闻布局不变。

### 10.3 无动画执行清单

- 关闭图表入场、更新动画、数字滚动、自动滚屏、跑马灯。
- 抽屉、弹窗、侧栏直接显示，不滑入、淡入或缩放。
- 删除通过setTimeout逐步自动“复核通过”或播放智能处理过程的逻辑。
- 操作立即给出确定结果；真实异步文件处理可显示静态“处理中”并防重复点击，不用人为延时。
- 新闻轮播保留直接换图，可手动选择；默认不自动抢焦点。
- 静态进度条可以展示真实计算进度，不动画增长。
- 第三方Modal、Tabs等组件也需检查自身动画配置；不能只删除页面CSS就宣称全站无动效。

### 10.4 现阶段不能替代的验证

本轮是源码分析和布局方案，未启动浏览器实测。因此不承诺“现有组件直接套上必然美观”。
实施时需逐页验证主内容宽度、长文本、空状态、长表格、意见输入、角色切换和不同屏幕尺寸，再按需要做小范围CSS修正。
验收截图为静态截图，不用动画视频代替功能验证。

## 十二、分批交付与验收标准

A批：框架和mock底座
- 顶栏保留、三角色、共同项目条、项目与程序数据、稳定ID、状态操作和持久化。
- 验收：切换角色不重置业务，项目范围正确；新建计划和项目不再混成一个对象。

B批：准备与执行
- 按页接入资料、分析、测试、证据、底稿与发现，重点解决保存和生成。
- 验收：三类型有专业内容；一个样本能真正形成底稿及待办；退回补充能重新送审。

C批：成果与闭环
- 审核中心、项目报告、外部意见登记、签发送达、整改核验、档案、首页与看板。
- 验收：三角色完成连续路径，报告不被整改阻塞，所有视图同步。

D批：静态视觉验收和清理
- 逐页三分辨率检查、真实点击回归、无效按钮和重复片段清理。
- 代码检查按仓库规范执行type-check、lint和build；已有基线问题单独记录，不借机全仓格式化。
- 功能检查覆盖正常、退回、无问题、异议、延期、重开、刷新及越权。
- 本轮方案文档不运行构建类检查，不声称已经通过业务或视觉验收。
